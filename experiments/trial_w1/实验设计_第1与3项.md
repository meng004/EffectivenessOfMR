# 一周可行性试验：第 1 项与第 3 项实验设计（Windows 运行版）

日期：2026-11-10。适用对象：在 Windows 电脑上独立执行，结果带回本目录 `trial_w1/results/`。

## 0. 目的与范围

| 项 | 要回答的问题 | 通过判据（事前冻结，不得事后修改） |
|---|---|---|
| 第 1 项 | OpenMC v0.15.2 能否从源码构建，CRAM 小算例能否稳定运行 | 构建成功；CRAM 算例两次运行输出 SHA-256 相同；单次 ≤ 10 分钟 |
| 第 3 项 | 能否在 `openmc.deplete` 的 Python 层生成足量、可运行、分层的句法变异体 | 「方程项」层与「非方程项」层各 ≥ 30 个**可运行且被测试执行到**的变异体 |

不在本次范围：ONIX（第 2 项）、Mull/OpenMOC（第 4 项）、历史缺陷（第 5 项）、事前预测揭盲（第 6 项）、蒙特卡洛输运。

本试验只判断「能不能做」，不产出论文结论。但第 3 项的产物（变异体清单、分层标签、MR 与参考预言两套判定）可直接作为后续正式实验的第一批数据，因此分层标签必须在看结果之前冻结。

## 1. 运行环境：用 WSL2，不用原生 Windows

- **理由**：OpenMC 的 C++ 核依赖 HDF5、POSIX 构建链，官方安装文档以 Linux/macOS 为主，Windows 一般经 WSL 运行（需你核对当前文档）；cosmic-ray 在 Linux 下最稳。
- **要求**：Windows 10 2004+ 或 Windows 11；WSL2 + Ubuntu 24.04；磁盘空余 ≥ 10 GB；内存 ≥ 8 GB。
- **关键**：所有文件放在 WSL 的 Linux 文件系统（`~/mrtrial`），**不要放在 `/mnt/c/...`**，否则构建和数千次变异运行会慢一个数量级。

在 PowerShell（管理员）执行一次：

```powershell
wsl --install -d Ubuntu-24.04
```

重启后进入 Ubuntu，把本目录的 `harness/` 复制进去（在 Ubuntu 中，`/mnt/c/...` 换成你实际放置本目录的位置）：

```bash
mkdir -p ~/mrtrial && cp -r "/mnt/c/<你的路径>/trial_w1/harness" ~/mrtrial/
```

## 2. 第 1 项：构建与 CRAM 小算例

### 2.1 构建

```bash
bash ~/mrtrial/harness/setup_wsl.sh 2>&1 | tee ~/mrtrial/setup.log
```

脚本做四件事：装依赖 → 克隆 v0.15.2 → 构建并安装 C++ 核 → 以**可编辑模式**安装 Python 包到 `~/mrtrial/venv`。可编辑安装是第 3 项的前提：cosmic-ray 改的是源码文件，import 必须指向这份源码。

脚本末尾会打印 `openmc.deplete.cram` 的文件路径，**必须位于 `~/mrtrial/openmc/` 之内**，否则第 3 项无效。

### 2.2 算例设计

玩具衰变链（`harness/toy_chain.xml`），两条互不连通的链：

- 链 1：I135 → Xe135 → Cs135（稳定）
- 链 2：Sr90 → Y90 → Zr90（稳定）

半衰期取近似值（只是测试载荷，不作物理结论）；时间步 1 天；初值两条链首核各 1e20。纯衰变、无反应率，因此不需要任何核数据库或输运计算。矩阵由 OpenMC 自己的 `Chain.from_xml` + `Chain.form_matrix` 组装，再用 `CRAM48` 求解。这样第 3 项的变异能同时落到「矩阵组装」和「求解器」两处。

### 2.3 运行与判定

```bash
source ~/mrtrial/venv/bin/activate && cd ~/mrtrial/harness
python cram_case.py ../results/cram_run1.json && python cram_case.py ../results/cram_run2.json
python -c "import json;a,b=(json.load(open(f'../results/cram_run{i}.json')) for i in (1,2));print('SAME' if a['sha256']==b['sha256'] else 'DIFF', a['seconds'], b['seconds'])"
```

**通过**：输出 `SAME`，且两个秒数都 ≤ 600。

## 3. 第 3 项：分层句法变异

### 3.1 被变异的文件

`openmc/deplete/` 下三份被算例实际执行的文件：`cram.py`、`chain.py`、`nuclide.py`。其余文件不变异：测试不执行它们，变异体只会全部"存活"，没有信息量。

### 3.2 开工前必须核对的 API（约 30 分钟）

以下三处是按记忆写的，**先读 v0.15.2 源码确认**，不符就按源码改 `mrlib.py`：

```bash
cd ~/mrtrial/openmc/openmc/deplete
grep -n "def form_matrix" -A 25 chain.py        # rates 参数的类型与访问方式
grep -n "class ReactionRates" -A 30 reaction_rates.py
grep -n "CRAM48\|def __call__" cram.py          # CRAM48 的调用签名
```

如果 `form_matrix` 必须依赖输运对象、30 分钟内搭不出零反应率输入：改用 `mrlib.build_A_ref()` 作为 MR 测试的矩阵，并把 `chain.py` 从变异范围中剔除。这样方程项层只剩 `cram.py`，需在结果中如实记录。

### 3.3 两套判定：MR 与参考预言

同一批变异体各跑两次：

| 判定 | 脚本 | 含义 |
|---|---|---|
| MR 判定 | `run_mr.py` | 5 条结构 MR，任一失败即杀死；每条 MR 的结果写入输出（`MRVERDICT 名称 pass/fail`） |
| 参考预言 | `run_oracle.py` | 与 `scipy.linalg.expm` 在**手写独立矩阵**上的结果比较，不经过 OpenMC 的任何代码 |

两者组合得到：参考预言判错、MR 判对 = 漏报；参考预言判对、MR 判错 = 误报。这正是后续论文要的混淆矩阵；本次只要求数据能产生，不分析。

5 条 MR（全部基于方程 dN/dt = A·N 的代数性质）：

| 编号 | MR | 依据 |
|---|---|---|
| MR1 | 初值放大 2 倍，输出放大 2 倍 | 线性 |
| MR2 | 两链初值分开算再相加 = 合起来算 | 叠加 |
| MR3 | 走两个 1 天 = 走一个 2 天 | 半群 |
| MR4 | 每条链总原子数守恒 | 衰变链闭合、末端稳定 |
| MR5 | 只给链 1 初值，链 2 各核保持为 0 | 零块／不可达结构 |

预期：MR1、MR2 对任何线性求解器都成立，抓不到「矩阵组装错」类变异。这是有意保留的，它会在数据里直接显示「哪类 MR 对哪层代码无效」。

### 3.4 健康基线：冻结容差前先测误报

在**未变异**代码上：

```bash
for i in 1 2 3; do python run_mr.py; done; python run_oracle.py
```

三次 MR 全部 `pass`、参考预言 `pass` 才能继续。若某条 MR 在健康代码上失败，只能整体放宽 `RTOL`（记录原值与新值），不得逐条调；然后重测三次。**此后 `RTOL` 冻结。**

### 3.5 分层标签：看结果之前冻结

编辑 `harness/layers.csv`，对三份文件里的**每一个函数**标一层：

- `equation`：计算方程项或其解的代码（衰变常数、分支比、矩阵组装、CRAM 系数与求解）。
- `non_equation`：解析、校验、数据结构、I/O、`__repr__` 等。

规则：按函数整体标，不按行；**两人独立标注**，各存一份（`layers_A.csv`、`layers_B.csv`），以 A 版运行，κ 留到后续计算。标完立刻记录哈希，之后不得改：

```bash
sha256sum layers*.csv | tee ../results/layers.sha256
```

### 3.6 覆盖率：剔除没被执行到的变异体

```bash
pip install coverage
coverage run --include="*/openmc/deplete/*" run_mr.py && coverage json -o ../results/cov.json
```

### 3.7 运行 cosmic-ray

先确认版本与命令（不同版本命令名有差异）：

```bash
cosmic-ray --version; cosmic-ray --help | head -30
```

然后：

```bash
bash run_cr.sh 2>&1 | tee ../results/cr.log
```

`run_cr.sh` 对 3 个文件 × 2 套判定生成 6 个会话（`results/*.sqlite`），每个变异体超时 60 秒。预计数千个变异体，单个 2–4 秒，总计约 2–6 小时；可以挂着过夜。

### 3.8 汇总与判定

先核对 sqlite 列名（`classify.py` 假定 `mutation_specs.start_pos_row`、`work_results.output` 等列，按 cosmic-ray 8.x 编写）：

```bash
sqlite3 ../results/cram_mr.sqlite .schema
```

列名不符就改 `classify.py` 里的 SQL。然后：

```bash
python classify.py --cov ../results/cov.json ../results/*_mr.sqlite ../results/mr_mutants.csv
python classify.py --cov ../results/cov.json ../results/*_oracle.sqlite ../results/oracle_mutants.csv
```

终端会打印每层的计数。**通过**：`equation` 与 `non_equation` 两层中，`covered=1`、`worker=normal`、`test ∈ {killed, survived}` 的变异体各 ≥ 30。`layer=unlabeled` 必须为 0（否则说明 `layers.csv` 漏标，补标后要重新记哈希并在日志里写明）。

另随机抽 10 个存活变异体人工看 diff，记录其中等价变异体的个数。这个数决定后续「漏报」能否直接按存活数计算。

## 5. 失败时怎么判

| 情况 | 判定 | 下一步 |
|---|---|---|
| C++ 核构建失败 | 第 1 项不通过 | 记录报错；先只装 Python 包（`pip install -e`，不需要 C++ 核也能跑 CRAM），第 3 项照做 |
| CRAM 两次输出不同 | 第 1 项不通过 | 记录差异位置；检查 BLAS 线程数（设 `OMP_NUM_THREADS=1` 重跑） |
| `form_matrix` 搭不起来 | 第 3 项降级 | 按 §3.2 改用手写矩阵，只变异 `cram.py` 与 `nuclide.py` |
| 某层可运行变异体 < 30 | 第 3 项不通过 | 记录实际数；这本身是结论：Python 层不足以支撑分层设计，需上 C++ 变异（第 4 项） |
| 健康基线 MR 失败 | 暂停 | 记录哪条 MR、残差多大；这是误报的第一个实例，比通过更有价值 |

## 6. 已知局限

- 玩具链只有 6 个核素、纯衰变，矩阵非常小，不代表真实燃耗刚性。
- 句法变异体仍在 Python 层，OpenMC 的 C++ 输运核不在范围内。
- `mrlib.py` 中 `form_matrix` 与 `ReactionRates` 的用法、`classify.py` 中的 sqlite 列名、cosmic-ray 命令名，均按记忆编写，未在 v0.15.2 和 cosmic-ray 实装上验证，§3.2、§3.7、§3.8 给出了核对命令。
